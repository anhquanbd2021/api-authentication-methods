Method guide

Six methods, six different questions

Every authentication method answers a slightly different question about the caller. This page maps each one to what it proves, how it fails, and when to reach for it.

Fixture secrets only. The lab uses a shared demo secret and fake credentials so you can watch verification succeed and fail — none of it leaves your browser.

Header credentials

Sent with every request

Method 01

API Key

A bearer string identifying a client — anyone holding it is the client. No expiry, no scoping unless you build them.

Proves
Which partner is calling.
Fails when
Leaked — it works for anyone until rotated. Lab 1 rotates a leaked key live.
Use for
Server-to-server calls, public APIs, third-party integrations.
Method 02

Basic Auth

user:pass Base64-encoded in every request — an encoding, not a cipher.

Proves
Username + password, re-sent constantly.
Fails when
Any log, proxy, or capture decodes the password. HTTPS only, user-facing never.
Use for
Quick internal tooling, prototypes.

Tokens and delegation

Issued once, presented many times

Method 03

JWT

A signed payload the server verifies without a session lookup — stateless auth.

Proves
Who the user is and what they may do — if the signature holds.
Fails when
Payload is readable by anyone (secrets leak); stolen tokens work until expiry. Lab 2 tampers a claim and loses the signature check.
Use for
User auth, stateless microservices, mobile apps.
Method 04

OAuth 2.0

Delegation, not login — an app gets a scoped token; the user's password stays at the provider.

Proves
The user consented to a scope for this app.
Fails when
Tokens leak via browser URLs, or scopes grant more than needed. Lab 4 steps the code flow.
Use for
Third-party integrations, social login, delegated access.

Proof at the edges

Message integrity and machine identity

Method 05

HMAC

A signature computed over timestamp + body with a shared secret — integrity and freshness together.

Proves
The body is untampered and the sender knows the secret.
Fails when
No freshness window — a captured request replays verbatim. Lab 3 replays an hour-old delivery.
Use for
Webhooks, signed requests, financial APIs.
Method 06

mTLS

Both sides present certificates; the handshake fails if either chain is untrusted.

Proves
Cryptographic identity for both caller and server — before any data moves.
Fails when
Cert expiry causes self-inflicted outages; issuance needs real PKI. Lab 5 runs the handshake with a rogue CA.
Use for
Service mesh, zero-trust, financial infrastructure.

Architecture

How the demo is built

LayerBehaviorEvidence
Crypto corePure-JS SHA-256, HMAC, base64url, and HS256 JWT sign/verify — no dependencies, runs identically in browser and tests.public/crypto.mjs
Method enginesAPI-key registry with rotation, Basic build/decode/verify, webhook HMAC sign/verify with freshness window and nonce replay store.public/methods.mjs
Flow modelsStep models for the OAuth 2.0 authorization-code flow and the mutual-TLS handshake.public/flows.mjs
ServerZero-dependency static host plus /health and /version. No API calls — every check runs client-side.app/server.js

Run locally

Inspect the evidence

npm test        # crypto vectors + all six method engines + server
npm run prove   # one-line verdict per method, printed side by side
npm run check   # both
npm start       # serve the lab on :3000

The engines are plain ES modules — the same files the browser imports are the files the tests exercise.

Limits

What this demo does not claim

  • Pure-JS SHA-256 is correct (tested against published vectors) but not constant-time hardware crypto — it is a teaching implementation.
  • The OAuth and mTLS labs model the message flow; no real TLS handshake or provider round-trip happens.
  • Real webhook systems sign more than timestamp + body (e.g. AWS SigV4 canonicalizes the whole request) — the lab covers the principle, not every scheme.
  • Verification logic is real; the secrets are fixtures. Never reuse them.
